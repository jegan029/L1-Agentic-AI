# Controls matrix

> **Engineering input for review by a compliance professional.** This document is written by engineering. It is not legal advice, not an audit opinion, and not a claim of certification, attestation or conformity with any framework named here. The product holds no certification. Framework references are given at criterion, control or article level from engineering's reading and must be checked against the current published texts by a qualified reviewer before any customer relies on them.

Status: after Phase 6. Every row says what exists: **Implemented**, **Partial**, or **Not built**. A row marked Implemented names code that exists and tests that pass, and a CI step fails the build if it does not (`python -m tools.controls_matrix`, section 1). A row marked Partial says in words what it lacks. Three rows are Not built; they are listed in section 9 and nothing in the product does what they describe.

Evidence is from automated tests against mocks, hand-written fixtures, connector conversations written by hand from vendor documentation, a stand-in ServiceNow written by hand, identity providers faked in the tests, a PostgreSQL 16 container and a local Kubernetes cluster (kind). The only real external systems exercised so far are one ServiceNow developer instance (incidents, knowledge articles, and opening, noting and closing a standard change and asking for its approval; not reading a person's approval) and one hosted model provider (rank advice in Phase 1; the gateway with the rank, extract and interpret tasks once in Phase 5). **Every control about actions is evidenced against a mock scheduler and a mock ServiceNow**; the action pipeline has never run against a real instance. **The runner has only ever talked to a control plane in the same process, on the same machine or in the same test cluster.** "Implemented" is an engineering statement that the code exists and its test passes. It is not an audit result.

Related: [target architecture](target-architecture.md), [threat model](threat-model.md), [delivery plan](delivery-plan.md), [security guide](security-guide.md), [ASVS self-assessment](asvs-self-assessment.md).

## 1. How to read this

- **Code** and **Test** are paths relative to the repository root, written in backticks. A name in backticks beside a path (a function, a class, a constraint, a test) is in one of the files that cell names. `CI job` followed by a name is a job in `.github/workflows/ci.yml`.
- **Status**: Implemented (phase), Partial (phase) with what is missing, or Not built.
- **The check.** `python -m tools.controls_matrix` reads this file. For each Implemented row it fails if a path does not exist, a name is not in the files beside it, or a CI job is not defined. Given the results of a test run (`--junit`), it also fails if a test the row names did not run or did not pass; in CI a skipped test fails too. It is run in the `tests` job after the test suite. It checks that the matrix is true to the repository. It does not judge whether a control is adequate, and it cannot see whether a CI job that a row names has ever passed: where a job has not yet been observed on the hosted runner, the row says so.
- Framework abbreviations: SOC 2 = AICPA Trust Services Criteria; ISO = ISO/IEC 27001:2022 Annex A; ASVS = OWASP Application Security Verification Standard chapter; LLM = OWASP Top 10 for LLM Applications 2025; DORA = Regulation (EU) 2022/2554; AI Act = Regulation (EU) 2024/1689; RMF = NIST AI RMF 1.0 function; 42001 = ISO/IEC 42001:2023; SR 11-7 = US Federal Reserve and OCC model risk guidance; SOX = IT general control domain.

These are starting points for the customer's and our privacy reviewers. In the single-tenant deployment the customer is the controller and operates the system; our role depends on the support model. In a hosted deployment we would be a processor.

### 4.2 Lawful basis notes

For the customer's assessment. The processing supports IT operations and security of the customer's own systems; legitimate interests (Art. 6(1)(f)) and, for regulated firms, legal obligation (Art. 6(1)(c)) for operational resilience are the bases most likely to be considered. Special category data is not intended to be processed; free-text tickets can contain it, which is one reason for redaction and for the option to disable model use.

### 4.3 Retention and erasure

**None of this is built (AU-05).** The product deletes nothing: there is no retention period, no erasure function and no legal hold. What follows is the intended design, kept so that a reviewer can comment on it.

- Retention would be configurable per tenant per data class (operational records, evidence, audit), with defaults confirmed by the reviewer.
- Erasure: operational records and the identity mapping table would be erasable per data subject. The audit chain holds pseudonymous ids and redacted payloads so that erasing the mapping removes identifiability without breaking the chain. Whether this satisfies Art. 17 in the customer's context needs privacy review; Art. 17(3)(b) and (e) may also apply to audit records.
- Legal hold would override expiry and be itself audited.
- Until then, a customer who must erase or expire data does so in the database, as its owner, knowing that removing audit rows breaks that tenant's chain from that point.

### 4.4 Sub-processors

None in the single-tenant deployment with the model disabled. When a model provider is enabled, that provider is a recipient chosen by the customer in the single-tenant shape, or our sub-processor in the hosted shape. A list is maintained at [`docs/sub-processors.md`](sub-processors.md) and the provider allow list (ML-03) is the technical enforcement.

### 4.5 Data residency

Single-tenant: wherever the customer deploys. Model requests go to the region configured per tenant; requests to other regions are refused in code (ML-03). Hosted: region per tenant, to be designed with that offering.

### 4.6 DPIA template

Delivered as [`docs/dpia-template.md`](dpia-template.md) in Phase 5, a template for the customer's privacy function to complete, with these sections: description of processing and purposes; necessity and proportionality; data inventory (from 4.1); recipients and transfers; risks to individuals (wrongly closed incident affecting a service, disclosure to a model provider, excessive retention, staff monitoring through audit logs); measures (rows AC-05, ML-02, ML-03, AU-05, EX-01); residual risk; consultation and sign-off.

## 9. Gap list

Things this matrix does not cover, or that remain open after Phase 6.

**Not built.** AU-04 (export to a SIEM), AU-05 (retention, legal hold, a write-once evidence store) and CR-04 (encryption at rest, which is the platform's). Also not built, and named in the rows above: mutual TLS between runner and control plane (CR-03), an audit viewer screen (AU-07), acceptance of an existing normal change (SD-05), an import to match the export (RS-05), and any restriction of outbound traffic by the chart (DP-01).

**Defined and never run in CI.** The bill of materials (SC-02) and image signing (SC-07) have not executed anywhere, so neither has produced a result. The dependency audit and the image scan (SC-03) were each run once by hand and have not run as CI jobs.

1. **No independent assurance.** No SOC 2 report, no ISO 27001 certificate, no penetration test. All are organisational and commercial steps outside this codebase.
2. **Organisational controls.** Policies, personnel security, vendor management, incident response for our own company, business continuity, training. Most SOC 2 and ISO 27001 controls are of this kind and none are addressed here.
3. **Real system behaviour unverified.** Controls are evidenced against mocks and fixtures only. That includes a control that changes a production scheduler: the force start has never run against Autosys, and the change and approval calls have never run against ServiceNow. Evidence from a real ServiceNow, Autosys, Splunk, Dynatrace or identity provider does not exist. The runner has never run in a customer network, behind a proxy, or against a control plane it reaches over the internet.
4. **Platform-level encryption and backup** are provided by the customer's infrastructure in the single-tenant shape. We supply defaults and documentation; the evidence is theirs.
