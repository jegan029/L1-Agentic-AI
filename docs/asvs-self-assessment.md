# OWASP ASVS self-assessment

> **Engineering's own reading, not a verification.** Nobody independent has assessed this product against ASVS. This document goes through the chapters of ASVS 4.0.3 and says, for the API and the dashboard, what is in place, what is not, and what has not been looked at. It is **by chapter, not by requirement**: a requirement-by-requirement assessment has not been done, and a chapter marked "largely met" may still fail individual requirements. Level 2 is the target. Use it to decide where to look, not as evidence of conformance.

Each entry points at the controls matrix row that names the code and the test. "Not assessed" means exactly that.

| Chapter | Position | What is in place | What is not, or not assessed | Rows |
|---|---|---|---|---|
| V1 Architecture, design and threat modelling | Largely met | A threat model by trust boundary; ADRs for each significant decision; one execution path; access control and tenant isolation enforced in one place each; components separated by what they hold | No secure development lifecycle document. No independent design review | Threat model; EX-04, EX-11, AC-05 |
| V2 Authentication | Met by delegation, with gaps | Sign-in is the customer's identity provider (OIDC with PKCE, state and nonce; SAML with signed assertions). No passwords are stored except one break-glass hash (scrypt). Sign-in attempts are rate limited and audited. Machine callers use random tokens stored as SHA-256 hashes with an expiry | Multi-factor authentication, password policy and account recovery are the identity provider's. The break-glass account is a single shared secret with no second factor. Not run against a real identity provider | AC-01, AC-04 |
| V3 Session management | Largely met | Server-side sessions; the cookie is `HttpOnly`, `Secure`, `SameSite=Lax`; absolute and idle timeouts; sign-out revokes; a CSRF token on state-changing requests; session ids are random and only their hash is stored | No list of a user's sessions and no "sign out everywhere". No re-authentication before a sensitive action such as approving a change | AC-07 |
| V4 Access control | Largely met | Deny by default: a route without a declaration stops start-up. Routes name permissions; roles map to permissions in a fixed, tested table. The tenant comes from the credential, never from the request. Row level security as a second line. Separation of duties in the service and in constraints | Permissions are per tenant, not per object: anyone who can read incidents can read all of the tenant's incidents. No periodic access review report, only a list of role mappings | AC-02, AC-03, AC-05, SD-01, SD-04 |
| V5 Validation, sanitisation and encoding | Largely met for what reaches a connector | Request bodies are parsed into typed models. Connector parameters are checked against closed schemas and allow lists before any connector code runs; an empty allow list denies. SOP parameters are bound from the ticket by a declared pattern and type. SQL is built by the query builder with bound parameters. Commands are argument lists, never shell strings. The dashboard renders text through React, which escapes it | The SOP editor accepts JSON that is validated as an SOP, not line by line against a published schema. Output encoding for values written back to ServiceNow relies on the Table API treating them as text; not assessed against a customised instance | EX-02, EX-09 |
| V6 Stored cryptography | Partly met | Nothing sensitive is encrypted by the product because nothing sensitive is stored by it: credentials are references. Signatures are Ed25519 from a maintained library; hashes are SHA-256; the break-glass hash is scrypt; random values come from the operating system | Keys are files, read at start-up, with no rotation procedure and no hardware protection. Data at rest is encrypted by the platform or not at all | CR-01, CR-03, CR-04 |
| V7 Error handling and logging | Largely met | Errors returned to a caller do not say which check failed. Operational logs redact message text by pattern and never contain model output. The audit log is separate, append-only, hash-chained, and written in the same transaction as the change | Redaction is pattern matching and will miss some content. No log shipping, no alerting, no SIEM export. Time comes from the host and is not checked | AU-01, AU-06, AU-04 |
| V8 Data protection | Partly met | Responses are sent `no-store`. Caller contact fields are never sent to a model. A data inventory and a DPIA template exist. An export of the tenant's data exists | No retention or deletion. No classification of fields beyond the inventory. Evidence from tools is stored as collected and may contain personal data | ML-02, RS-05, AU-05 |
| V9 Communication | Largely met | TLS verification is on for every outbound connection and cannot be turned off outside demo mode. The runner refuses a control plane that is not `https`. The chart does not render an ingress without TLS. HSTS is sent | Traffic between an ingress and the API pod is plain HTTP unless the API is given a certificate or a mesh is used. No mutual TLS in the product. Cipher suites and protocol versions are the platform's defaults; not assessed | CR-02, CR-03 |
| V10 Malicious code | Partly met | Dependencies are pinned with hashes; base images by digest; static analysis and a secret scan block in CI; no code is loaded at run time from anywhere; only first-party connectors are registered | The dependency audit and image scan are defined in CI and have only been run by hand, once. The bill of materials and image signing have never run. No review for deliberately hidden functionality | SC-01, SC-02, SC-03, SC-07 |
| V11 Business logic | Largely met | The outcomes that matter are enforced as invariants with tests that search for a violation: no resolution without verification; no write without a decision; an approval is for one exact action; the same write is made at most once per incident; rate limits on actions per target | Limits are per tenant rule, not learned. No detection of unusual sequences of otherwise permitted actions | EX-01, EX-04, EX-05 |
| V12 Files and resources | Largely met where it applies | No file upload. The file share connector reads only under allow-listed path prefixes, by path segment. The Git source reads blobs from a bare mirror and checks nothing out. An export refuses to write into a directory that is not empty | The browser connector, a preview, loads pages from allow-listed hosts in a browser that is not sandboxed; it is not in the default image | EX-09 |
| V13 API and web service | Largely met | One JSON API with typed request models, a body size limit, a rate limit, strict CORS (no wildcard), and the OpenAPI document behind a permission. Webhooks and runner requests are signed, fresh and used once | The rate limit is per process and per client address, so it is weak behind a proxy. No API versioning beyond the runner's routes. No GraphQL, no SOAP | AC-06, AC-08, AC-09 |
| V14 Configuration | Largely met | The service refuses to start in an unsafe configuration (no credentials, wildcard CORS, a database role that can bypass isolation, protections switched off outside demo mode). Containers are non-root with a read-only root filesystem. Security headers on every response, and a content security policy that allows the page's own origin only | Settings given through the environment are not audited by the product. Debug and demo modes exist and are guarded by configuration, not removed from the build | SC-04, DP-01 |

## What would change this assessment

- A requirement-by-requirement pass by someone who did not write the code.
- A penetration test of a deployed instance, including the dashboard in a browser, the runner's routes, and the path from ticket text to connector parameters.
- Running against a real identity provider and a customised ServiceNow instance.
